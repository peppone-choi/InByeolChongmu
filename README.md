# 인별총무 (InByeolChongmu)

인스타그램 DM으로 상품을 판매하는 1인 셀러를 위해, 답장 초안 작성부터 주문 정리와 송장 입력 자료 준비까지 돕는 에이전트를 개발합니다.

## 누구를 위한 에이전트인가요?

옷이나 생활용품을 DM으로 판매하거나 공동구매를 운영하며, 하루 수십 건의 문의를 혼자 처리하는 판매자를 대상으로 합니다. DM 내용을 엑셀에 옮기고, 주문과 송장을 찾아 고객에게 답하는 반복 업무를 줄이는 것이 목표입니다.

현재는 가상 고객을 바탕으로 한 기획이며, 실제 판매자의 수요와 시간 절감 효과는 아직 검증하지 않았습니다.

## 어떤 업무를 돕나요?

- 복사해 붙여넣은 텍스트 DM을 문의 유형별로 분류합니다.
- 상품표·판매 정책·주문 기록을 근거로 판매자 말투의 답장 초안을 작성합니다.
- 주문 정보를 추출하고, 빠진 필수 정보를 안내합니다.
- 판매자가 입금을 확인하고 승인한 주문을 기록하고, 아이디나 이름으로 조회합니다.
- 판매자가 직접 입력한 발송·송장 기록을 저장하고 정정 이력을 남깁니다.
- 확정·미발송 주문을 공통 발송명단 엑셀로 내보내고 열 이름·순서·필수값을 설정합니다. 실제 택배사 업로드 양식은 대상 선정 후 별도로 검증합니다.

답장은 판매자가 검토 후 직접 보냅니다. 입금 확인과 주문 확정도 판매자가 맡습니다. 송장 자료 내보내기는 송장 자동 발급이나 프린터 출력과 다릅니다.

## 진행 상황

**2026-11-06 기준: 채팅 API에 Flue 실행기를 연결했습니다. OpenAI가 대화방 맥락을 읽어 자료 도구를 호출하고, TypeSafe Jev 분류와 코드 검증을 거친 분석·답장 초안을 반환합니다. Docker 단일 컨테이너 실행도 지원합니다. React 웹 화면에서 DM을 입력하면 같은 에이전트를 호출하고, 답장·주문 초안·근거·도구 기록을 표시합니다.**

### 원래 제품 흐름과 남은 핵심

`DM 붙여넣기 → 분류·자료 조회·초안/주문 추출 → 주문 후보 저장 → 판매자 입금 확인·확정 → 주문 조회 → 발송·송장 기록/정정 → 택배 양식 엑셀`

현재는 **DM 분석 → 주문 후보 저장·수정 → 판매자 입금액/입금자/배송지 확인 → 주문 확정·재고 차감**까지 DB·API·웹으로 연결했습니다. 분석 JSON은 자동 저장·확정되지 않으며, 웹에서 ‘주문으로 저장’을 눌러 시작합니다. **수동 발송·송장 등록과 사유/변경 전후 이력, 확정·미발송 주문의 공통 명단 엑셀·열 설정도 구현했습니다.** 실제 택배사 접수 프로그램과의 호환성은 미검증입니다. 이 업무 흐름을 기준으로 [복귀 후 실행 순서](docs/implementation-plan.md#복귀-후-실행-순서)를 따릅니다.

상품·옵션·정책 추가/수정/삭제, 상품·정책 엑셀 미리보기/검증 후 가져오기, 현재 데이터 XLSX·JSON 내보내기와 상품/정책·주문·채팅의 독립 초기화를 제공합니다. 상품/정책 초기화는 샘플 없이 비우고 주문·대화를 유지합니다. **주문 삭제·초기화는 이미 차감한 재고를 복원하지 않습니다.** 주문 삭제는 해당 발송/정정 이력도 지우고 그 주문이 포함된 택배 파일을 폐기합니다. 주문 전체 초기화는 택배 파일/이력도 지우며 열 설정은 유지합니다. 채팅 초기화는 앱 기록과 전용 Flue DB를 비우며 외부 모델 서비스 기록·다운로드한 파일은 지우지 않습니다.

**가상 DM 40건 평가 실행기와 동명이인 주문 검토를 추가했습니다.** 조회 결과·견적·고객 원문에 따라 검토 사유와 처리 상태를 보완했습니다. DM-028의 다른 계정 주문은 후보 ID만 보여 주고, 입금자명과 입금 주장은 최신 고객 원문에서 별도로 표시합니다. 실제 모델 평가와 후속 재검증 결과는 [검증 계획](docs/test-plan.md#다른-계정-입금과-일괄-dm-검증)에 기록했습니다. 초기 기획 대비 미완성·부분 지원·실제 자료가 필요한 항목과 단계별 완료 조건은 [기획 대조와 다음 구현 순서](docs/implementation-plan.md#초기-기획과-남은-차이)에 정리했습니다.

### 지금 되는 것

- Hono 채팅 API로 고객별 대화방을 만들고 메시지를 SQLite에 저장합니다. 같은 고객의 다른 상담 방, 다른 판매자의 자료를 구분하고 중복 요청을 거절하거나 재사용합니다. 실행 기한은 SQLite에 저장해 재시작으로 늘어나지 않습니다.
- 상품·정책·주문 가상 JSON을 실제 SQLite에 적재해 읽습니다. 가격·할인·배송비 계산, 판매 일정 조회와 허용 문서 파일 읽기가 동작합니다.
- 자료 도구 6개를 HTTP·CLI·MCP stdio·Flue에서 사용합니다. Flue가 도구를 선택해 실제 SQLite·문서를 읽고 `submit_analysis`로 검증된 결과를 제출합니다. TypeSafe 키가 있으면 `classify_inquiry`도 사용합니다.
- 웹에서 상품명·별칭·옵션별 가격/재고·판매 마감과 정책을 수정하고 SQLite에 저장합니다. 배송비·할인·출고일 문구는 저장 값에 맞춰 생성하며 오래된 자료로 만든 초안 복사는 차단합니다.
- DM에서 현재 고객의 주문을 찾지 못하면 원문에 나온 이름으로 판매자 검토용 후보 ID를 조회합니다. 검토 화면의 후보 버튼에서 주문 상세를 열어 대조할 수 있습니다.
- DM 검토 → **일괄 DM**에서 고객 아이디·상담 맥락·원문을 건별로 입력합니다. 최대 10건(요청 전체 64 KiB)을 접수한 뒤 한 건씩 분석합니다. 다시 열면 저장된 상태를 확인하고 필요한 건만 이어서 처리할 수 있습니다. 클레임과 확인 필요 건을 먼저 표시합니다.
- 주문 화면에서 아이디·수령인 이름·상태로 찾고 미확정 주문을 보완합니다. 실제 입금액·입금자명·배송지 확인 후 확정할 때 최신 가격·정책·재고·마감을 서버에서 재검사하고 원자적으로 차감합니다. 중복 확정으로 다시 차감하지 않습니다.
- 설정에서 현재 데이터 XLSX·JSON을 내보내고 상품·정책 엑셀을 미리보기 후 가져옵니다. XLSX의 주문·대화·분석·일괄 접수 시트는 조회용이며 다시 가져오지 않습니다. 실제 택배 양식이 아닙니다. 파일 SQLite는 재시작 후 보존하고 인메모리는 테스트에 사용합니다. 별도 DB 서버는 필요 없습니다.
- 주문 화면에서 실제 발송 후 택배사·송장번호·시각을 등록합니다. 정정은 사유가 필수이며 변경 전후·판매자·시각·버전을 함께 보존합니다. 재고·금액은 바뀌지 않습니다.
- 택배 엑셀은 선택 주문을 먼저 검증해 확정·미발송 건만 포함하고 제외 사유를 보여줍니다. 이전 내보내기 이력과 중복 접수 확인, 기존 파일 재다운로드를 제공합니다. 열 이름·순서·포함 여부·필수값을 설정할 수 있습니다.
- `.env.local`과 `.env`로 설정을 받습니다. 필요한 키 이름은 [.env.example](.env.example)에 있으며 키 없이 서버·도구 검증을 실행할 수 있습니다.
- [제작 문서](docs/README.md), [부트스트랩 계획](docs/implementation-plan.md), 가상 DM 40건과 자료 검사·회귀 검증을 확인할 수 있습니다.

### 아직 안 되는 것

- Hermes·OpenAI Agents API·AI Gateway 추론 경로와 업무 캘린더·Sheets 계정 연결은 후속입니다. 현재 실행 경로는 Flue → OpenAI 직접 호출이며, Jev는 별도의 분류 도구입니다.
- 실제 택배사 양식 어댑터·접수/송장 발급·실시간 배송 조회는 미구현입니다. 택배사 미정에 따라 현재는 공통 명단과 열 설정을 제공합니다.
- Docker는 단일 서버·영속 볼륨·Bearer 토큰 또는 브라우저 세션으로 실행합니다. 사용자별 운영 인증·보관/삭제 정책·다중 서버 공유는 없으므로 실제 고객 자료나 공개 서비스에 사용하기 전 추가 구현이 필요합니다.

### 설치와 실행

Node.js **26.5.1 이상, 27 미만**과 npm을 사용합니다. 검증 버전은 `.node-version`에 기록했습니다.

```sh
npm ci
cp .env.example .env.local
npm run db:seed
npm run dev
```

기존 `.env.local`이 있으면 복사로 덮어쓰지 마세요. API는 `http://127.0.0.1:3000`에서 실행합니다. `.env.local` → `.env` 순서로 읽으며 셸 환경 변수가 우선합니다. 기본 DB는 `.local/inbyeol.sqlite`이며 `AGENT_BACKEND=flue`, `AGENT_MODEL=openai/gpt-5.5`, `OPENAI_API_KEY`를 설정하면 채팅 요청에서 모델을 호출합니다. `TYPESAFE_API_KEY`는 선택 사항입니다. 기본 `disabled`에서는 자료 도구만 사용하고 채팅은 저장 후 `503`을 반환합니다.

`npm run build` / `npm start`로 컴파일·실행하고 `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm test`로 검사합니다. 상세 API·도구·대화방·엑셀·백업 명령과 현재 한계는 [백엔드 사용법](docs/backend.md)에 있습니다.

### 웹 화면과 채팅 API

터미널 두 개에서 각각 실행합니다. 기존 `.env.local`의 키를 사용하며 브라우저에 키를 전달하지 않습니다.

```sh
npm run dev
```

```sh
npm run web:dev
```

`http://127.0.0.1:5173`에서 **DM 추가 → 고객 아이디·상담 맥락·원문 입력 → 추가하고 분석**을 누릅니다. 에이전트가 방 이력을 읽고 자료 도구를 선택하며, 실제 도구 진행 상태를 2초 간격으로 조회합니다. 결과에 답장 초안·상품/수량/금액·누락값·근거가 나타납니다. 같은 방의 ‘이어서 받은 DM’으로 후속 대화를 분석합니다. 상품·정책 메뉴의 수정/저장으로 자료를 바꾸고, 자료 변경 경고가 붙은 초안은 최신 자료로 다시 분석합니다. 복사 직전에도 서버 버전을 확인합니다. 초안은 검토·수정 후 복사해 직접 전송합니다.

방·원문·모델 결과·도구 기록은 SQLite에 보존됩니다. 초안 수정·검토 표시는 화면 메모리에만, 글자 크기/근거 표시 설정만 브라우저 저장소에 둡니다. 새로고침은 모델을 자동 호출하지 않습니다. 통신 결과가 불명확하면 같은 요청 ID로 결과를 확인하고, 저장된 실패를 다시 분석할 때는 새 ID로 모델을 재호출합니다. 초기 상품·정책·주문은 **가상 자료**이므로 실제 판매 자료를 연결하기 전 실제 고객 업무에 쓰지 마세요.

Vite의 로컬 프록시가 서버에서만 env의 `LOCAL_API_TOKEN`을 붙입니다. 백엔드 포트를 바꾸면 두 터미널에 같은 `PORT`를 지정하세요. 빌드 결과는 `npm run build && npm run web:build && npm start` 후 `http://127.0.0.1:3000`에서 확인합니다. 이 경우 연결 화면에 서버 `LOCAL_API_TOKEN`을 입력하면 8시간 HttpOnly·SameSite=Strict 세션을 발급합니다. 서버 재시작 후 다시 연결해야 합니다. `npm run web:preview`는 정적 미리보기만 제공하므로 API 통합 확인은 Hono 서버를 사용하세요.

화면 흐름과 한계는 [UX 설계](docs/ux-flows.md#현재-웹-연결)를 따릅니다.

### Docker와 실제 모델 검증

`.env.local`에 위 설정과 32자 이상 무작위 `LOCAL_API_TOKEN`을 넣은 뒤 실행합니다. 키와 DB는 이미지에 넣지 않습니다.

```sh
docker compose up -d --build
docker compose logs --tail=20 api
docker compose down
```

포트는 `127.0.0.1:3000`으로 공개하며 웹 화면도 함께 제공하며 API는 Bearer 토큰 또는 연결 화면에서 발급한 세션으로 인증합니다. 두 SQLite 파일은 `inbyeol-data` 볼륨에 보존됩니다. `down -v`는 자료를 삭제하므로 사용하지 마세요. 외부 배포에는 별도 HTTPS·운영 인증이 필요합니다. 상세 설정·백업은 [백엔드 사용법](docs/backend.md#docker-실행)을 따릅니다.

`npm run verify:agent`는 env 키를 사용해 **유료 실제 호출**을 실행합니다. 격리된 가상 자료와 2026-11-05 기준 시각으로 대화 맥락·62,000원 계산·TypeSafe 도구·중복 재전송·원본 보존을 확인하고 임시 DB를 정리합니다. 자동 CI에는 포함하지 않습니다.

가상 DM 40건의 대상은 `npm run --silent eval:agent`로 확인합니다. `npm run --silent eval:agent -- --live`는 실제 모델을 호출하고 사례별 결과를 JSONL로 출력합니다. `--case DM-009`로 단건을 선택할 수 있습니다. 결과 해석과 수동 검토 방법은 [검증 계획](docs/test-plan.md#가상-dm-평가-실행기)을 따릅니다.

### 첫 버전에서 제외하는 것

인스타그램 직접 연동·자동 발송, 은행 입금 자동 확인, 택배사 API 송장 발급, 사진 인식, 다계정·다인원 지원, 홍보 글 작성, 결제·쇼핑몰 기능은 다루지 않습니다.

## 문서·샘플 검사

Python 3로 `python3 docs/samples/validate.py`를 실행합니다. JSON 구조·ID 참조·금액·예시 계약·문서 링크를 검사하며, 앱 실행이나 모델 성능 테스트는 아닙니다.

자료 검사 도구의 회귀 검증은 `python3 -m unittest discover -s docs/tests -v`로 실행합니다. 변조 반례 거절과 정상 과거 주문 허용, 발송 명령 예시의 필수값·버전·시각 정합성을 검사하며 실제 주문 상태를 변경하지 않습니다.
