# 사용자 여정·유스케이스·화면 흐름

상태: 역할은 판매자 1명입니다. 아래 UC는 목표 흐름이며, 현재 `web/`은 실제 채팅 API와 연결한 React 검토 화면입니다. 초기 자료는 가상 샘플이며 주문 후보 저장·입금 확인/확정·재고 반영·수동 발송/정정·공통 명단 내보내기를 웹에서 실행합니다. 여러 DM 일괄 처리와 실제 택배사 양식은 후속입니다.

## 사용 전·중·후

- 사용 전: 판매자가 상품표·정책·주문 자료를 준비합니다. 화면에서 연결 상태·자료 버전을 확인합니다.
- 처리 중: DM을 고객별로 붙여넣고 원문과 결과를 대조합니다. 예외를 먼저 보고 답장을 수정·복사합니다.
- 처리 후: 은행 앱에서 입금을 확인하고 주문을 확정합니다. 확정 주문을 조회하거나 내보냅니다.

## UC-01 상품 문의 답장 / R-01~04

전제: 상품·정책 자료가 준비되어 있습니다. 판매자가 DM-001을 넣고 분석합니다. 결과에 유형·재고·실측·할인 근거가 보이며 초안을 수정·복사합니다. 복사 버튼은 실제 DM 전송으로 표시하지 않습니다. 정보가 없는 DM-005는 확인 필요를 표시합니다.

## UC-02 주문 정리와 확정 / R-05~07

판매자가 DM-002를 분석하면 원문 옆에 두 SKU·수량·수령인·총액이 보입니다. 초안을 저장해도 주문은 대기 상태이며 재고는 바뀌지 않습니다. 은행 앱 확인 후 금액·입금자명·수령지를 확인하고 확정합니다. 최신 재고·버전이 다르면 재검토로 돌아갑니다. DM-003은 누락값을 묻는 흐름으로 분기합니다.

## UC-03 배송 조회·클레임 / R-03·04·08

DM-008을 분석하면 O-0001의 발송 기록과 송장만 표시합니다. DM-009는 동명이인 후보를 판매자가 고르기 전 초안을 생성하지 않습니다. DM-011은 우선 표시하고 환불 확정 없는 최소 초안으로 판매자에게 넘깁니다.

## UC-04 여러 건 처리 / R-10

고객 아이디와 대화 블록을 각각 추가합니다. 처리 결과는 건별 카드로 나뉘고 확인 필요·클레임을 우선 표시합니다. 한 건이 실패해도 다른 결과는 유지하며, 재시도는 선택한 건만 처리합니다.

## UC-05 확정 주문 내보내기 / R-09

판매자가 확정 주문과 택배 양식을 선택합니다. 미발송·필수값 충족 여부, 제외 사유, 이전 내보내기 이력을 확인하고 내려받습니다. 실제 송장 접수·출력은 기존 프로그램에서 진행합니다.

## UC-06 수동 발송·송장 기록과 정정 / R-08·12·13

판매자가 기존 택배 프로그램에서 실제 발송을 확인하고 주문 상세에서 택배사·송장번호·발송 시각을 등록합니다. 확정 주문에만 등록할 수 있고 성공 시 조회 화면에 저장된 발송 기록이 보입니다. 서버가 저장 완료를 확인하기 전에는 발송 완료로 표시하지 않습니다.

오입력은 발송 정보 정정에서 최신 값과 수정 사유를 확인하고 저장합니다. 중복 클릭·재시도는 기존 결과를 재사용하고, 다른 수정으로 버전이 바뀌었으면 최신 기록을 다시 확인합니다. 실패해도 입력을 보존하며 재고·주문 금액은 바꾸지 않습니다. 상세 계약과 완료 조건은 입출력 명세 7절 및 AC-18~21입니다.

## 최소 화면 구성 제안

- **입력·검토**: 고객별 원문, 유형·우선순위, 초안, 근거, 추출 필드, 누락·오류, 수정·복사·후보 저장.
- **주문 목록·상세**: 상태·검색·후보 선택, 입금 확인·확정, 송장 기록, 내보내기.
- **자료 설정**: 상품·정책 자료와 버전, 택배 양식 연결 상태. 새 대시보드를 별도 요구하지 않습니다.

빈 상태·처리 중·근거 없음·모델 실패·저장 실패·중복 확정·재고 충돌·내보내기 부분 제외 화면이 필요합니다. 확정 버튼은 차단 이유를 함께 표시하고, 분석·저장·확정·복사·발송을 서로 다른 행동으로 설명해야 합니다.

## 현재 웹 연결

사용자가 승인한 **차분하고 선명한 업무 도구**의 작업대 구성을 유지합니다. 밝은 중성 바탕·파란 강조색·Lucide 아이콘·이름이 붙은 메뉴를 사용합니다. 데스크톱은 목록→원문/답장→검토 정보이며 좁은 화면은 목록→대화→검토 정보를 순서대로 엽니다.

**DM 추가**에서 고객 아이디·상담 맥락·텍스트를 입력하면 새 방을 만들고 `POST /api/chat`을 호출합니다. 같은 고객도 다른 맥락은 새 방으로 만들 수 있습니다. 현재 방의 ‘이어서 받은 DM’은 같은 방 ID로 전송하며 에이전트가 최근 방 이력과 실제 자료 도구를 사용합니다. 고정된 샘플 답장을 새 입력에 붙이지 않습니다.

실행 중 2초마다 방 상세를 읽어 도구 이름과 진행·성공·실패를 표시합니다. 완료 후 기록은 접어서 원문·답장 검토 공간을 확보합니다. 모델 결과의 상품·옵션·수량·계산 금액·수령값·누락/오류·근거 ID/버전을 표시합니다. 도구 원문이나 키는 화면에 보내지 않습니다. 과거 assistant 메시지는 전송 전 초안임을 표시합니다.

수신 원문과 분석은 SQLite에 저장되며 새로고침 후 복원합니다. 복원 자체로 모델을 호출하지 않습니다. 통신 오류는 같은 요청으로 결과를 확인하고, 종료된 모델 실패는 새 ID로 명시적으로 다시 분석합니다. 처리 중 같은 방의 새 DM은 막고 다른 방은 조회할 수 있습니다. 요청 실패가 다른 방 결과를 덮어쓰지 않습니다.

답장 수정·복사·검토 표시는 화면에서 수행하고 편집/검토는 새로고침하면 사라집니다. 표시 설정만 브라우저에 저장합니다. 주문 후보 저장 후 주문 화면에서 필수 정보를 보완하고 입금 확인·확정합니다. 확정 시 재고를 한 번 차감합니다. 실제 DM 전송은 판매자가 직접 합니다. 초기 자료는 가상 샘플이며 실제 고객 업무 검증은 별도입니다.

상품·정책은 서버 SQLite의 현재 자료/버전을 표시하고 수정/저장합니다. 가격·재고·소재·기존 실측·옵션·마감일과 정책을 편집하며 ID/SKU는 유지합니다. 배송비·할인·출고일 문구는 구조화 값과 맞춰 자동 작성합니다. 저장 충돌 시 입력을 보존하고 최신 자료를 다시 열 수 있습니다. 수정 전 자료를 쓴 초안은 경고·복사 차단하며 명시적으로 재분석합니다. 복사 직전에도 서버 버전을 조회합니다. 설정은 API 연결, 실행기/모델·키 설정 여부와 실행 제한을 읽으며 키 원문은 받지 않습니다. 키 설정 여부는 실제 공급자 성공 보장이 아닙니다.

개발 화면은 동일 출처 프록시를 사용합니다. Docker/빌드 화면은 연결 암호를 입력해 HttpOnly 세션을 얻습니다. 연결·로딩·빈 목록·오류·진행·초안 없음 상태를 구분합니다. 연결 세션은 단일 상점 접근용이며 사용자별 운영 인증은 후속입니다.
