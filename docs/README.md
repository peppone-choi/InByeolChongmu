# 제작 문서 안내

2026-11-05 기준. 모든 제작 문서는 초안이며 기능 구현·성능 검증 완료를 뜻하지 않습니다.

## 읽는 순서와 문서별 책임

1. [PRD](prd.md): 누구의 어떤 문제를 어디까지 해결하는지.
2. [요구사항](requirements.md): 구현할 동작과 제약의 식별자.
3. [사용자 여정·화면 흐름](ux-flows.md): 실제 사용 장면과 유스케이스.
4. [입력·출력 명세](io-spec.md), [가상 샘플](samples/README.md): 구체적인 자료와 결과 계약.
5. [데이터·상태 규칙](data-model.md), [아키텍처](architecture.md): 데이터 관계와 처리 책임.
6. [인수조건](acceptance-criteria.md), [검증 계획](test-plan.md): 완료 판정과 검증 방법.
7. [운영·보안 기준](operations.md), [구현 순서·결정 목록](implementation-plan.md): 운영 준비와 다음 작업.

[초기 기획서](planning.md)는 원문과 외부 피드백의 출처·배경을 보존합니다. 현재 제작 계약은 위 문서에서 관리하고, 충돌하면 묵시적으로 한쪽을 택하지 않고 함께 수정합니다. 가격·정책의 샘플 값은 `samples/` JSON이 기준입니다.

## 원문·확정 사항·제안 구분

- 원문 기준: DM 붙여넣기, 판매자 직접 발송·입금 확인·확정, 최소 기능과 제외 범위.
- 이번 요청으로 확정: 가상 자료 제작, 입출력 구체화, 제작 문서 뼈대 작성.
- 설계 초안: JSON 필드, 상태, 화면 구성, 단계별 구현 순서. 실제 셀러 검증 전입니다.
- 샘플 전용: 상품·가격·할인·연락처·주소·재고·주문과 날짜. 운영 정책으로 쓰지 않습니다.

## 마피아 MCP에서 확인한 보완점

`review` 절차와 결정 지점별 검색 4회를 사용했습니다. 카드가 완성된 문서 목록을 반환한 것은 아니며, 아래 판단을 바탕으로 프로젝트에 필요한 문서 구성을 도출했습니다.

- 「요구사항을 바로 기능으로 만들지 않고, 여정표를 먼저 쓰고 범위를 정한다」 (`k731d767fab`): 기능 목록 외에 여정·화면 흐름을 추가했습니다.
- 「유스케이스가 나오지 않는 기획은 구현하지 않고, 개발로 넘길 정보는 유스케이스와 디자인만 추린다」 (`k8e38ba10a3`): 인수조건으로 연결되는 유스케이스를 작성했습니다. 실제 화면 시안은 아직 없습니다.
- 「원자료가 불완전하다고 산출물 작성을 미루지 않는다」 (`k199b6a6e07`): 가상 자료로 계약을 구체화하고 실제 셀러·택배 양식 등 미확인 사항을 분리했습니다.
- 「동작 확인을 사용자에게 넘기기 전에 브라우저 자동화로 직접 end-to-end 테스트한다」 (`k82f4ec7618`): 문서 검증과 향후 앱 검증을 구분했습니다.
- 「같은 기준의 결과물이 여러 건 남으면 한 건씩 승인받지 않고 모두 만든 뒤 한 번에 검수받는다」 (`kd7bd8ee8d1`): 필요한 문서 초안을 한 번에 작성했습니다.

단일 판매자용 초기 버전에 맞춰 오류 목록은 입출력 명세에, 개인정보·장애·배포 기준은 운영 문서에, 결정 기록·미정 사항은 구현 계획에 합쳤습니다. 별도 SLA·대규모 인프라 설계·정식 API 명세서는 지금 만들지 않습니다. 필요해지는 시점은 구현 계획에 적었습니다.
