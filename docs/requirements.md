# 요구사항 명세

상태: 구현 전 초안. `R-` 식별자는 인수조건·구현 작업에서 공통으로 사용합니다.

## 기능 요구사항

- **R-01 입력**: 판매자·고객 아이디·텍스트·기준 시각·자료 스냅샷을 받습니다. 빈 아이디·빈 본문을 구분해 안내하고, 여러 건의 고객 경계를 보존합니다.
- **R-02 분류**: 상품 문의, 주문 접수, 입금 주장, 배송·주문 조회, 클레임, 판매 무관으로 분류합니다. 텍스트가 없는 사진은 지원 불가로 구분합니다. 혼합 문의의 대표 유형 우선순위는 클레임 → 주문 접수 → 입금 주장 → 주문 조회 → 상품 문의 → 판매 무관입니다. 답변 가능한 부수 질문도 버리지 않습니다.
- **R-03 근거 조회**: 표준 상품·옵션 ID와 주문 ID로 후보를 조회합니다. 별칭 충돌·동명이인·조회 실패를 구분하고 임의 선택하지 않습니다.
- **R-04 초안**: 초안마다 근거 ID·스냅샷·필드를 제공합니다. 정보가 없으면 확인 필요로 표시합니다. 판매 무관·사진 입력·주문 중복 후보에는 고객 정보가 담긴 답장을 만들지 않습니다.
- **R-05 추출**: 상품·옵션·수량·이름·연락처·주소·입금자명을 추출합니다. 누락과 잘못된 값을 구분하고 원문을 보존합니다.
- **R-06 계산·검증**: 금액은 정수 원 단위로 코드가 계산합니다. JSON·필수값·옵션·수량·연락처 형식·마감·가용 재고와 초안의 근거 수치를 검사합니다.
- **R-07 확정**: 분석은 주문·재고를 변경하지 않습니다. 입금·수령지의 판매자 확인과 최신 데이터 재검사를 거쳐 확정하며, 중복 요청·동시 확정에 따른 중복 기록·재고 차감을 막습니다.
- **R-08 주문 조회**: 아이디 또는 이름으로 조회합니다. 복수 결과는 판매자에게만 후보로 표시하고 고객 답장은 식별 후 작성합니다. 현재 배송 상태·도착일을 추측하지 않습니다.
- **R-09 내보내기**: 확정된 미발송 주문 중 필수값이 갖춰진 건을 대상 택배 양식으로 내보냅니다. 내보냈다는 이유로 발송 완료·송장 발급 상태로 바꾸지 않습니다.
- **R-10 일괄 처리·복구**: 여러 DM의 결과·실패를 건별로 보존하고 실패한 건만 재시도할 수 있어야 합니다. 부분 실패를 전체 성공으로 보고하지 않습니다.

## 공통 제약

- **R-11 개인정보·신뢰 경계**: 첫 버전은 판매자 1명 범위입니다. DM 속 지시로 정책·권한·승인 규칙을 바꾸지 않습니다. 가상 자료는 외부로 발송·조회하지 않습니다. 실제 데이터의 접근·보관·삭제 기준을 운영 전 확정합니다.
- **R-12 검증·추적**: 요청 ID, 자료 버전, 검증 결과, 승인 기록으로 오류를 추적합니다. 원문 개인정보를 일반 로그에 기록하지 않습니다. 미검사·불일치·정상·실패 상태를 구분합니다.

## 외부 의존과 미정 사항

실제 택배 양식, 데이터 저장소, 모델·런타임, API 방식은 미정입니다. 주소 검색은 기본 검증 이후의 보조 연동이며 결과 없음·복수 후보·실패를 별도로 다룹니다. 상세 계약은 [입출력 명세](io-spec.md)를 따릅니다.
