## 1. 한 줄 목표

인스타그램 DM 판매자가 대화를 붙여넣으면, 근거 있는 답장 초안과 주문 기록·송장 입력 자료를 받아 반복 입력과 조회 시간을 줄인다.

## 2. 대상과 현재 업무 (원문 기준)

대상은 인스타그램에서 옷·생활용품을 판매하거나 공동구매를 여는 1인 셀러입니다. 원문의 고객 A는 가상 인물이며, 매일 수십 건의 DM을 처리하는 상황을 가정합니다.

- 상품·재고·사이즈 문의에 매번 직접 답합니다.
- DM의 주문 내용을 엑셀에 옮기고, 은행 앱에서 입금을 확인합니다.
- 수령인·주소·연락처를 택배사 프로그램에 다시 입력합니다.
- 배송 문의나 민원이 오면 엑셀과 송장 기록을 뒤져 주문을 찾습니다.

해결할 문제는 도구 사이의 반복 입력, 주문 조회 지연, 누락과 오타입니다. 판매자가 직접 판단할 예외와 고객에게 답장을 보내는 책임은 유지합니다.

## 3. 성공 장면 (원문 기준)

공동구매 다음 날, 판매자가 고객 아이디와 DM 대화를 붙여넣습니다. 결과에서 문의 유형, 답장 초안, 근거, 추출한 주문 정보와 확인할 항목을 함께 봅니다.

판매자는 초안을 수정·복사해 인스타그램에서 직접 보냅니다. 주문은 은행 앱에서 입금을 확인한 뒤 확정하고, 저녁에는 확정 주문을 택배사 양식으로 내려받습니다. 여러 건 입력도 첫 버전 범위에 포함하되, 구현은 단건 흐름부터 검증합니다.

## 4. 첫 버전에 넣을 것

원문의 최소 기능을 다음 다섯 흐름으로 묶습니다. 모두 구현 예정입니다.

1. **DM 입력과 분류**: 고객 아이디와 텍스트 대화를 받아 상품 문의, 주문 접수, 입금 확인, 배송·주문 조회, 교환·환불·클레임, 판매 무관으로 분류합니다. 여러 건 입력은 대화 경계를 구분해 처리합니다.
2. **근거 있는 답장 초안**: 상품표·판매 정책·주문 기록을 조회하고 판매자 말투로 작성합니다. 근거는 상품표 행, 정책 문구, 주문 건을 다시 찾을 수 있도록 표시합니다.
3. **주문 추출과 누락 확인**: 상품·옵션·수량·수령인 이름·연락처·주소·입금자명을 추출하고 금액을 계산합니다. 누락 항목은 확인 요청 초안으로 돌려줍니다. 원문과 추출값을 나란히 비교할 수 있어야 합니다.
4. **승인 후 기록과 조회**: 판매자가 입금을 확인하고 확정한 주문을 저장하고 재고를 반영합니다. 고객 아이디나 이름으로 주문·상태·송장번호를 찾습니다. 조회 결과가 여러 건이면 임의로 선택하지 않습니다.
5. **송장 자료 내보내기**: 확정 주문을 선택한 택배사의 일괄 등록 엑셀 양식으로 내보냅니다. 송장 발급과 출력은 판매자가 기존 프로그램에서 수행합니다.

## 5. 승인과 예외 처리 경계

- 모든 답장은 초안까지만 만듭니다. 실제 전송은 판매자가 합니다.
- 고객의 “입금했어요”만으로 입금 완료나 주문 확정을 처리하지 않습니다.
- 환불·교환·보상·정책 밖 할인·가격 흥정은 판매자 판단으로 넘깁니다.
- 재고 부족이나 공구 마감 건은 예약 또는 거절을 임의로 결정하지 않습니다.
- 상품을 특정할 수 없거나 주문이 없거나 동명이인이면 추가 확인을 요청합니다.
- 근거가 없는 소재·재입고일·배송 일정은 만들어내지 않습니다. 송장번호만으로 현재 배송 상태를 확인했다고 표현하지 않습니다.
- 클레임은 사과와 확인 의사만 담은 초안과 함께 우선 표시합니다. 판매 무관 대화는 초안을 만들지 않고, 사진만 있는 입력은 판단 불가로 표시합니다.

## 6. 뒤로 미룰 것과 이유 (원문 범위)

- **인스타그램 연동·자동 발송**: 첫 버전은 복사·붙여넣기와 판매자 검토 흐름으로 검증합니다.
- **은행 연동·입금 자동 확인**: 은행 앱 확인과 판매자 확정을 유지합니다.
- **택배사 API 송장 발급**: 기존 프로그램에서 쓸 양식 내보내기까지 다룹니다.
- **사진 인식, 다계정·다인원 운영**: 텍스트 DM과 판매자 1명에 집중합니다.
- **홍보 글 작성, 결제·쇼핑몰 기능**: DM 대응과 주문 정리 범위 밖입니다.

유료 요금제, 자동 말투 학습, 매출 대시보드는 첫 버전의 완료 조건에 넣지 않습니다. 원문의 요금과 시간 절감 효과는 검증 전 가설입니다.

## 7. 필요한 입력 자료와 도구 후보

- 상품표: 상품명·옵션·가격·실측·재고·공구 마감일.
- 판매 정책: 배송비·출고 요일·할인·교환 및 환불 기준·입금 계좌·FAQ.
- 주문 기록: 고객 아이디·수령인·연락처·주소·상품·금액·입금일·상태·송장번호.
- 말투 자료: 판매자가 실제로 보낸 DM 20~30개.
- 택배 자료: 실제 사용할 택배사의 일괄 등록 엑셀 양식.

원문은 Google Sheets 읽기·쓰기, 언어 모델, 배송조회 링크 생성을 도구로 제시하고, Flue·Jev·OpenAI Agents API 등을 제작 후보로 언급합니다. 현재 채택하거나 연결한 도구는 없습니다. 기술 선택은 입력·출력 흐름과 실제 양식을 확인한 뒤 정합니다.

실제 고객 자료를 쓰기 전에는 사용 권한과 보관·삭제 기준을 정합니다. 저장소와 테스트에는 비식별·가상 자료를 사용하고, 실제 DM·주소·전화번호·인증 정보는 커밋하지 않습니다. 이는 초기 검증을 위한 추가 제안입니다.

## 8. 성공 기준과 검증 방법

아래 수치는 원문의 목표이며 아직 측정하지 않았습니다. 실제 과거 DM 50건과 정답 데이터가 준비되기 전의 가상 자료 검증은 실제 성능 검증과 구분합니다.

### DM 50건 평가 목표

- 문의 유형 분류 정확도 **90% 이상**.
- 수정 없이 또는 한두 단어 수정으로 보낼 수 있는 초안 **70% 이상**.
- 상품표·정책에 없는 정보를 지어낸 초안 **0건**.
- 주문 정보 추출 필드 정확도 **95% 이상**.
- 빠진 필수 정보 감지율 **100%**.

평가 방법 제안: 판매자가 문의 유형·추출값·누락 항목·허용 답변 근거를 정답으로 정하고, 초안 사용 가능 여부도 판정합니다. 추출 정확도는 주문 관련 평가 필드 중 정확한 필드 비율, 누락 감지율은 정답 누락 항목 중 감지한 항목 비율로 계산합니다. 대상 사례 수와 초안 생성 대상 수를 함께 기록하고, 누락 사례가 없다고 감지율을 100%로 보고하지 않습니다.

### 실제 사용 1주 후 목표

- 배송·민원 문의의 평균 주문 조회 시간: 가정한 **5분에서 30초 이내**.
- 하루 DM 대응 시간: 도입 전의 **절반 이하**. 원문의 예시는 3시간 → 1.5시간입니다.
- 주소·연락처 오타로 인한 배송 사고: **0건**.

도입 전 시간을 실제로 측정하고, 도입 후에도 검토·수정·복사 시간을 포함해 비교합니다. 현재 기준선과 효과는 모두 미측정입니다.

## 9. 실행 순서와 단계별 완료 조건 (제안)

1. **업무와 자료 확인**: 실제 셀러의 반복 문의·주문 확정 방식과 택배 양식을 확인합니다. 상품표·정책·비식별 DM·주문 예시를 준비하고 필수 필드를 정리합니다.
2. **단건 처리 검증**: 한 건의 DM에서 분류·추출·누락 안내·근거 있는 초안이 이어지는 흐름을 만듭니다. 정상 주문, 정보 누락, 모호한 상품, 근거 없음, 클레임을 검증합니다.
3. **기록과 조회 연결**: 승인 전에는 확정 기록·재고가 바뀌지 않고, 승인 후에만 반영되도록 만듭니다. 반복 확정 요청이 주문 중복이나 재고 중복 차감으로 이어지지 않는지 확인합니다.
4. **여러 건 처리와 내보내기**: 대화 간 고객 정보가 섞이지 않는지 확인합니다. 선택한 택배사의 실제 양식으로 가상 주문을 내보내 필드·열 순서·필수값을 검증합니다.
5. **50건 평가와 사용 검증**: 위 품질 목표를 평가하고 미달 원인을 수정합니다. 실제 고객 자료 사용 조건을 갖춘 뒤 1주 사용 효과를 측정합니다.

이는 초기 구현 순서 제안이며, 현재는 어느 단계의 제품 기능도 구현되지 않았습니다. 현재 작업 순서는 [구현 계획](implementation-plan.md)에서 관리합니다.

## 10. 구현 전에 확정할 사항

문서 작성은 아래 답변 없이 진행합니다. 실제 고객이나 정책을 임의로 확정하지 않습니다.

- **첫 검증 대상**: 실제 셀러 1명과 검증할 판매 흐름을 정해야 합니다. 추천은 상품군과 공동구매 회차를 좁혀 시작하는 것입니다.
- **택배사와 양식**: 대상 택배사와 실제 업로드 양식이 필요합니다. 추천은 현재 사용하는 양식 1개부터 지원하는 것입니다.
- **자료와 정책**: 테스트 자료 사용 권한, 실제 가격·배송비·할인·교환 및 환불 기준이 필요합니다. 추천은 비식별·가상 자료로 먼저 검증하는 것입니다.

- **상담 통합**: 채널톡은 인스타그램 DM을 연결해 응대하는 기능을 안내합니다. [공식 인스타그램 연동 안내](https://docs.channel.io/help/ko/categories/인스타그램-2b91e980)
- **DM 자동화**: Manychat은 인스타그램 응답·DM 자동화를, Chatfuel은 댓글에서 DM으로 이어지는 자동화를 안내합니다. [Manychat 공식 연결 안내](https://help.manychat.com/en/articles/17741886-how-to-connect-instagram-to-manychat), [Chatfuel 공식 안내](https://chatfuel.com/for-creators)
- **쇼핑몰·주문 관리**: 캠페이너스는 주문 관리와 굿스플로 송장 출력 절차를 안내합니다. [공식 주문 관리 안내](https://help.campaignus.me/ko/categories/주문관리v2-자주-묻는-질문-afca3c09)

답변에 포함된 제이폼의 인스타그램 폼 수집 방식과 Manychat·Chatfuel의 현재 Shopify 연동 범위는 이번 확인에서 검증하지 못했습니다. 도입 조건과 지원 기능은 별도 확인 대상으로 남깁니다.

인별총무의 차별화 가설은 **쇼핑몰로 옮기지 않고 기존 DM 대화에서 상품 근거·주문 기록·송장 자료를 이어 주는 것**입니다. 기존 서비스에 같은 기능이 없다는 결론은 아닙니다. 실제 셀러가 기존 도구 조합보다 편하다고 느끼는지 검증해야 합니다. 세 영역을 참고하되, 첫 버전의 인스타그램 직접 연동·자동 발송 제외 원칙은 유지합니다.

### 처리 단계를 나누고 코드로 검증하기

제안 흐름: `DM 분류 → 상품·주문 후보 조회 → JSON 추출 → 코드 검증·금액 계산 → 근거 기반 초안 → 결과 대조 → 판매자 확인`.

1. **분류·추출·초안의 책임 분리**: 단계별 입력·출력을 정의해 오류가 난 위치를 확인합니다. 각 단계마다 별도 모델 호출을 강제하는 것은 아닙니다. DM은 처리할 자료로 취급하고, DM 안의 지시가 판매 정책이나 승인 규칙을 바꾸지 못하게 합니다.
2. **JSON 구조와 값 검증**: 필수 키·타입·허용 옵션·양의 정수 수량을 코드로 검사합니다. 누락값은 임의로 채우지 않고 누락 상태로 보존합니다. 연락처는 원문을 보존하며 형식을 정규식 등으로 검사하되, 형식 통과가 실제 사용 번호나 소유자 확인을 뜻하지는 않습니다.
3. **계산은 코드가 담당**: 상품·옵션의 기준 가격, 수량, 확정된 할인 규칙과 배송비로 합계를 계산합니다. 중복 할인·배송비 조건이 불명확하면 확인 대상으로 돌립니다. LLM이 만든 금액을 정답으로 사용하지 않습니다.
4. **초안과 근거 대조**: 가격·수량·실측·재고 등 비교 가능한 수치를 근거와 대조하고 불일치하면 검토 없이 보낼 수 있는 초안으로 표시하지 않습니다. 같은 수치가 다른 상품·옵션에 붙는 오류도 확인합니다. 수치 일치는 소재·출고 약속·환불 조건 같은 문장 전체의 사실성을 보장하지 않으므로, 근거 확인과 50건 평가를 함께 유지합니다.
5. **상품 별칭 관리**: 상품표에 별칭 열을 추가하는 안을 반영합니다. 표준 상품·옵션 식별자에 연결하고, 별칭이 겹치거나 “그거”처럼 정보가 부족하면 후보와 확인 질문을 제시합니다. 별칭만으로 확정하지 않습니다.

### 주소 검색 API의 역할과 한계

제안된 [행정안전부 실시간 주소정보 조회(검색API)](https://www.data.go.kr/data/15057017/openapi.do)는 주소 검색어로 도로명주소·지번주소·우편번호 등을 조회하는 API이며 승인키가 필요합니다. 공식 소개는 확인했으나 실제 호출·연결은 하지 않았습니다.

후보 주소와 우편번호를 확인하는 보조 수단으로 검토합니다. 검색 결과가 있어도 고객이 의도한 주소인지, 상세 동·호수가 맞는지, 실제 배송 가능한지는 별도 확인이 필요합니다. 원문 주소를 자동으로 덮어쓰지 않고 원문과 후보를 함께 보여 줍니다.

기본 추출·누락 검증을 먼저 구현하고, 주소 API는 키·이용 조건·테스트 입력을 확인한 뒤 연결하는 순서를 제안합니다. 미조회·검색 결과 없음·복수 후보·API 오류를 구분하며, 검증을 못 한 경우 통과로 간주하지 않습니다. 외부 조회에는 이름·전화번호를 함께 보내지 않습니다.

### 추가할 검증 사례

JSON 형식 오류, 누락값, 잘못된 전화번호 형식, 상품 별칭 충돌, 옵션별 가격 혼동, 할인 경계, 근거와 초안 수치 불일치, 주소 복수 후보·검색 실패, API 장애를 검증 목록에 추가합니다. 코드 검증을 통과했다는 이유만으로 원문의 “지어낸 초안 0건” 목표를 달성했다고 보고하지 않습니다.

마피아 MCP에서 추가 피드백의 반영 범위를 재점검했고, **「처방 하나로 승인을 구하기 전에 '최선인가'를 대안·트레이드오프로 검토하고, 범위가 다른 개선은 별개 PR로 나눈다」** (`k02a37de65e`)의 “미검사와 통과를 구분한다”는 판단을 주소 조회와 결과 검증 기준에 반영했습니다.

후속 작업에서 가상 샘플과 [입력·출력 명세](io-spec.md)를 작성했습니다. 실제 셀러의 업무·정책·택배 양식은 여전히 확인이 필요합니다.
