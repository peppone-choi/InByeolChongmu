# 검증·평가 계획

상태: Node·Python 회귀 검사, Flue·OpenAI·Jev 연결 검사와 가상 40건 평가 실행기를 제공합니다. 실제 50건 평가와 제품 전체 인수는 후속입니다.

## 검증 단계

1. **자료 검증**: JSON 파싱, ID 고유성, SKU·주문 참조, 주문 금액, 사례 기대값, Markdown 링크를 확인합니다. 제품 동작 검증과 구분합니다.
2. **코드 단위 검증**: 추출값 스키마·연락처 형식·할인 경계·금액·수량·마감·근거 불일치 처리. 샘플 가격 규칙과 실제 정책을 혼용하지 않습니다.
3. **서비스 통합 검증**: 주문 저장·승인·상태 전이, 트랜잭션 실패 롤백, 재시도·중복 명령·동시 차감, 외부 의존 장애를 검증합니다.
4. **화면 E2E 검증**: UC-01~06을 브라우저에서 수행하고 원문·결과·상태·내보내기 파일·발송 정정을 확인합니다. 가상 자료만 사용하고 검증 후 이번 실행 데이터만 정리합니다.
5. **모델 품질·실사용 평가**: 가상 회귀 사례와 실제 비식별 평가를 분리합니다. 기능 통과만으로 실제 시간 절감 효과를 주장하지 않습니다.

## 자료와 인수조건 추적

[DM 40건](samples/dm-cases.json)의 `expected`는 필수 검증 항목입니다. `DM-002`만 [완전한 출력 예시](samples/analysis-example.json)가 있으며 나머지는 고정 문자열 정답이 아닙니다. `must_not_claim` 문자열 금지만으로 환각 여부를 판정하지 말고 근거와 의미를 함께 검토합니다.

어투·복수 발화·정정·생략·중복 전송·혼합 문의도 평가합니다. `conversation`과 `input.text`, [대표 대화 미리보기](samples/dm-examples.md)의 일치 여부를 자동 검사하며, 대화 원본은 실제 수집 DM이 아닌 가상 자료입니다. AC-22~23의 의미·분류 품질은 서비스 구현 후 별도로 실행합니다.

[인수조건](acceptance-criteria.md)의 모든 AC를 실행 결과에 연결합니다. DM만으로 만들 수 없는 동시 확정·재내보내기·자료 버전 충돌·주소 API 장애는 별도 서비스 시나리오로 작성합니다.

## 가상 DM 평가 실행기

`npm run --silent eval:agent`는 40건과 파일 지문을 표시하며 모든 사례를 `not_run`으로 기록합니다. 실제 모델 실행은 `npm run --silent eval:agent -- --live`로 시작합니다. `--case DM-009`를 추가하거나 반복해 사례를 지정할 수 있습니다. 초안 본문으로 수동 검토할 때는 `--include-drafts`를 추가하고 JSONL 출력을 Git에서 제외된 파일에 보관합니다. 예를 들어 `npm run --silent eval:agent -- --live --include-drafts > .local/agent-eval.jsonl`을 실행합니다. 실제 실행은 설정된 OpenAI·선택적 Jev를 호출합니다.

각 사례는 초기 자료를 적재한 인메모리 앱 DB와 새 임시 Flue DB로 `POST /api/chat`에 입력합니다. 정답·스냅샷 ID는 요청에 넣지 않습니다. 기준 시각, 파일 지문, 모델 설정과 한도, HTTP 상태·오류·모델 호출 수·경과 시간을 기록합니다. 응답의 분류·추출·금액·필수 필드·근거 ID·후보를 기대값과 대조하고 상품·정책·주문 원본과 자료 버전을 비교합니다. 평가 과정에서 청구 비용은 측정하지 않습니다.

`failed`는 자동 대조 불일치 또는 실행 오류, `manual_review`는 자동 대조를 만족하고 초안이나 의미 검토가 남은 사례, `passed`는 지정한 자동 항목을 충족하고 남은 수동 검토 항목이 없는 사례입니다. 입력 오류의 HTTP 거절과 분석 응답 형식을 따로 판정합니다. 평가 실패 또는 실제 실행 누락이 있으면 종료 코드 1을 반환합니다. CI는 고정 응답으로 평가 규칙과 실제 Flue의 도구 경계를 검사합니다.

DM-009 회귀는 후보 O-0002·O-0003의 ID만 반환하고 다른 계정의 주문 ID 조회 및 근거·답장 제출을 차단하는지 확인합니다. 스크립트 모델과 격리 DB를 사용한 화면 검사에서 데스크톱 및 320·375·414·768px에서 후보 버튼이 각각의 주문 상세로 연결되는 것을 확인했습니다.

### 2026-11-10 기준 실행 결과

Flue의 OpenAI `gpt-5.5` 및 Jev 설정으로 40건을 실행했습니다. 결과는 **자동 항목 통과 2건, 자동 항목 충족 후 사람 검토 13건, 자동 실패 25건, 미실행 0건**입니다. 모델이 실행된 38건의 경과 시간 중앙값은 16.768초이며 Flue 모델 호출은 205회입니다. Jev 호출과 청구 비용은 집계하지 않았습니다. 상품·정책·주문 원본과 자료 버전은 40건 모두 보존됐습니다.

실패 25건 중 7건은 모델 8회 한도에 도달해 HTTP 503으로 끝났습니다. 확인 사유 코드 18건, 상태 14건, 분류 11건이 달랐으며 항목은 한 사례에서 중복될 수 있습니다. 사진 전용 DM-013은 지원 불가로 분류했으나 확인 코드가 기대와 달랐습니다. DM-020은 HTTP 422로 모델 호출 전에 거절됐으며, 입력 거절의 채점 기준을 422로 바로잡아 별도 재검사했습니다. 분석 응답 형식과 확인 코드의 차이로 사례 결과는 실패입니다.

DM-009의 실제 모델은 3회 호출 후 O-0002·O-0003, `human_review`, `ORDER_AMBIGUOUS`와 `reply_draft=null`을 반환했습니다. 자동 항목을 충족한 13건에는 초안 12건과 별도 의미 검토 1건이 남았습니다. 상세 결과는 로컬의 `.local/agent-eval-2026-11-10-verified.jsonl`에서 확인할 수 있습니다.

### 검토 사유·상태 보완 후 재평가

동일한 40건, 기대값, 자료 지문, 모델 설정 및 60초·모델 8회·도구 16회 한도를 유지했습니다. 실패한 제출에는 검증 항목 이름을 기록해 반복 거절을 추적했습니다. DM-004·010·024는 사실 없는 확인 질문에 조회 근거가 요구됐고, DM-023은 명시적으로 바꾼 호수가 포함된 주소 전체가 원문 한 곳에 없다는 이유로 거절됐습니다. 기존 주문 변경·취소·교환 재현에서는 후보 ID 또는 클레임 상태·우선순위와 검토 사유가 맞지 않았습니다. 서버 문구, 고객 주소 정정 대조, 조회 근거와 검토 상태 정리로 해당 경로를 수정했습니다.

전체 재실행은 자동 통과 4건, 수동 검토 33건, 실패 3건입니다. DM-018은 기존 입금 대기 주문을 새 주문 초안 없이 반환할 수 있도록 검증 분기를 추가해 4회 호출로 자동 기준을 충족했습니다. 60초 제한에 걸린 DM-015는 같은 한도로 단독 재실행해 자동 기준을 충족했습니다. 후속 실행 4건을 포함한 사례별 최신 집계는 **자동 통과 4건, 수동 검토 35건, 실패 1건**입니다. 전체 실행과 후속 실행의 원본 보고서와 코드 지문을 별도로 보존했습니다.

최초 모델 한도 실패 7건은 전체 재실행에서 사례당 2~4회 호출로 자동 기준을 충족했습니다. 최신 사례 집계에서 검토 코드·처리 상태 불일치와 실행 오류는 0건입니다. DM-028은 판매자 검토 상태와 사유는 일치했고 다른 계정의 주문 후보와 입금자명·입금 주장 추출 기대값이 남았습니다. 상품·정책·주문 원본과 버전은 모든 비교에서 보존됐습니다. 청구 비용은 집계하지 않았습니다. 비교 보고서는 로컬의 `.local/agent-review-reevaluation-2026-11-10.jsonl`입니다.

### 다른 계정 입금과 일괄 DM 검증

동일한 가상 40건·기대값·자료 지문과 60초/모델 8회/도구 16회 한도로 전체 실행한 결과는 자동 통과 3건, 수동 검토 35건, 자동 실패 2건(DM-005, DM-009)이었습니다. 소재를 묻는 상품의 조회 결과가 하나이고 소재 값이 비어 있을 때에는 실제 조회 ID와 누락 사유를 남기고 확인 문구를 사용하도록 보완했습니다. 이름 뒤에 붙은 정중한 종결 표현을 인식해 DM-009의 검토 후보를 복원했습니다.

DM-005·009·028 및 기존 입금 사례 DM-018·029를 같은 기준으로 단건 재확인했습니다. 전체 실행에 후속 사례별 최신 결과를 합산하면 **자동 통과 4건, 수동 검토 36건, 자동 실패 0건**입니다. DM-028 최종 재확인은 4회 모델 호출(17.139초)로 O-0004와 고객 원문의 입금자명·입금 주장을 반환했습니다. 다른 계정 주문은 상세/답장/주문 초안에 사용하지 않았습니다. 수동 검토는 초안의 사실성·말투·사용 가능성과 금지 의미를 별도로 판정해야 한다는 뜻입니다. 실행별 지문·결과는 `.local/dm028-regression-*.jsonl`, `.local/dm028-final-v3.jsonl`, `.local/dm028-payment-verified.jsonl`, `.local/dm028-guard-verified.jsonl`에 보존했습니다.

AC-15 자동 통합 테스트는 DM-001·002·009·020을 같은 묶음으로 접수합니다. 혼합 성공·모델 실패·입력 오류, 방과 원문 분리, 재시작 후 같은 요청 재사용, 실패 건만 새 ID 재시도, 주문/재고 보존과 채팅 초기화를 검증합니다. 브라우저에서는 가상 입력으로 접수·순차 실행·실패 건만 재시도·결과 대화 열기를 확인했습니다. 320·375·414·768·1280px에서 가로 넘침을 검사했습니다.

임시 파일 SQLite와 실제 Flue·OpenAI·Jev로 AC-15의 네 건에 DM-028을 추가해 한 묶음으로 실행했습니다. 유효한 네 건의 자동 대조 항목이 모두 맞았고, DM-020은 모델 호출과 방 생성 없이 `HANDLE_REQUIRED`로 분리됐습니다. 상품·정책·주문은 그대로였습니다. 결과는 `.local/dm-batch-ac15-verified.jsonl`에 보존했습니다.

## 품질 평가 기준

실제 비식별 DM 50건을 평가 전 고정하고 정답·유형·관련 필드를 사람이 확인합니다. 기준은 분류 90% 이상, 초안 사용 가능 70% 이상, 근거 없는 생성 0건, 필드 추출 95% 이상, 누락 감지 100%입니다. 사례 분포·분모·미검사 수를 함께 기록합니다.

연락처·주소·SKU·수량·입금자명은 정규화 규칙을 정한 뒤 비교합니다. 초안 문장 전체 일치는 요구하지 않으며 사실성·누락·사용 가능 여부를 검토합니다. 누락 사례나 생성 초안이 없으면 해당 비율을 통과로 계산하지 않습니다.

실사용은 도입 전후 동일 업무의 시간을 기록하고 복사·검토·수정 시간도 포함합니다. 실제 고객 자료 권한과 보관 기준이 정해지기 전에는 실행하지 않습니다.

`tests/shipping.test.ts`는 실제 Commerce/Parcels와 HTTP/브라우저 API 계약을 사용합니다. 과거 주문·새 관리 주문의 발송/정정과 정규화 재시도·작업 간 키 충돌, 타 판매자·미확정/취소/이미 발송·오래된 버전·누락/시간대/미래/확정 전 시각 거절, 감사 기록 삽입 실패 시 전체 롤백을 검사합니다. 별도 프로세스 두 개의 등록 경쟁에서 하나의 이벤트/버전만 저장되는지 확인합니다. 재고·금액·수령인 보존과 에이전트 조회의 최신 송장도 대조합니다.

초기 주문 6건의 공통 명단 후보는 O-0002·0003·0006이며 다른 3건의 제외 사유를 검사합니다. 전화 문자열/수식 방지/숫자 금액·필수 우편번호 제외·열 설정 충돌·미리보기 후 발송 상태 변경·재내보내기 확인·같은 파일 ID 재시도·삭제 후 파일 폐기·주문 초기화의 이력 정리를 검사합니다. 실제 택배사 프로그램에 업로드한 검사가 아니며 AC-14의 실제 양식 통과를 뜻하지 않습니다.

격리된 SQLite를 연결한 Aside 브라우저에서 O-0006 발송 등록→송장 정정→버전 3·감사 이벤트 2건을 확인했습니다. 원본 상품 재고·주문 금액과 독립 대조해 불변을 확인했습니다. 공통 엑셀은 최초 6건 선택에서 3건 포함/3건 제외, 이후 전화 열 이름/순서와 배송메모 열 제외를 바꾼 파일은 2건·7열로 대조했습니다. 실제 다운로드의 앞자리 0 연락처는 문자열, 금액은 숫자이며 재내보내기 경고와 확인 전 생성 차단도 확인했습니다. 320·375·414·768px과 1440px에서 열 설정·발송 정정 폼을 확인했고 320px 날짜 입력의 넘침을 수정했습니다. 화면과 문서의 자료는 모두 가상입니다.
