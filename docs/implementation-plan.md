# 구현 순서와 결정 목록

상태: PR #6에 읽기 에이전트·웹/채팅, 주문 저장/확정·재고와 자료 CRUD/엑셀/독립 초기화를 구현했습니다. 아래 제품 흐름과 미구현 범위를 기준으로 다음 작업을 진행합니다. 현재 명령·제한은 [백엔드 사용법](backend.md), 전체 완료 판정은 [인수조건](acceptance-criteria.md)을 따릅니다.

## 현재 구현과 제품 완성의 차이

제품의 완료 흐름은 **DM 입력·분류 → 근거 기반 초안/주문 추출 → 주문 후보 저장·수정 → 판매자의 입금·수령지 확인 → 주문 확정·재고 반영 → 주문 조회 → 수동 발송/송장 등록·정정 → 확정 미발송 주문의 택배 양식 내보내기**입니다. 읽기 에이전트나 자료 편집 화면만으로 제품이 완성됐다고 보지 않습니다.

현재 구현은 단건 DM/방 맥락·Flue/TypeSafe 도구·코드 견적·구조화 분석·복사용 초안·SQLite 보존에서 주문 후보 저장/수정과 판매자 입금 확인·확정/원자적 재고 차감까지입니다. 상품/옵션/정책 CRUD, 엑셀 미리보기/검증 후 가져오기, XLSX·JSON 현재 데이터 반출과 독립 초기화도 제공합니다. 분석 JSON의 `order_draft`는 자동으로 주문이 되지 않습니다.

**아직 미구현**: 수동 발송/송장 정정과 이력, 실제 택배 양식, 일괄 DM 처리, 주문/대화 재가져오기. 상품·정책 가져오기는 전용 양식과 한글 열 별칭을 지원하며 임의의 엑셀 구조를 모델이 추측해 자동 변환하지 않습니다. 자동 테스트·소량 실검증은 전체 실제 DM 품질 통과가 아닙니다.

### 복귀 후 실행 순서

1. **DM에서 확정 주문까지 한 흐름 (구현)**: 검증된 분석에서 주문 후보를 저장하고 원문과 필드를 수정·대조합니다. 주문 목록/아이디·이름 조회, 판매자 입금 금액·입금자명·수령지 확인, 최신 자료 재검사, 주문 확정/전 품목 재고 반영을 DB·API·화면까지 연결합니다. AC-08~12의 중복·동시 마지막 재고·버전 변경·롤백을 검증합니다. 에이전트가 승인 없이 확정하지 않습니다.
2. **실제 발송 후 기록과 정정**: 확정 주문의 택배사·송장·발송 시각을 수동 등록하고 정정 사유/전후 이력을 보존합니다. AC-18~21을 실제 서비스로 검증하며 조회 결과는 저장된 발송 사실만 설명합니다.
3. **내보내기와 자료 준비**: 현재 상품·정책·주문·대화 데이터의 내보내기와, 확정 미발송 주문의 택배 양식 출력은 별개로 구현합니다. 자료 준비의 상품/정책 CRUD와 엑셀 미리보기/검증 후 가져오기, 현재 데이터 반출은 구현했습니다. 택배 양식은 실제 대상 양식을 확보해 AC-13·14로 검증하며 내부 공통 엑셀을 실제 택배 양식이라고 표시하지 않습니다.
4. **반복 작업·복구·평가**: 여러 DM의 경계/실패/재시도와 도메인별 초기화를 검증합니다. 가상 40건 전체, 이후 실제 50건과 1주 사용 검증은 별도로 수행합니다. 단계마다 서버만 만든 채 넘기지 않고 DB·API·화면·직접 실행까지 끝냅니다.

자료 관리·가져오기·기본 내보내기는 위 흐름의 입력 준비/결과 반출로 구현했습니다. 별도 설정 기능을 계속 늘리며 주문·발송 흐름을 미루지 않습니다.

### 사용자가 확정한 추가 요구

- 상품·정책은 기존 값 수정뿐 아니라 추가·삭제도 지원합니다. 과거 주문의 저장 당시 금액·발송 사실은 별도로 보존합니다.
- 상품·정책 초기화는 **샘플 없이 모두 비우며 주문과 대화는 유지**합니다. 재시작으로 샘플을 다시 채우지 않습니다.
- 주문 초기화와 채팅 기록 초기화는 각각 별도 동작이며 다른 데이터 영역을 함께 지우지 않습니다. 채팅 초기화는 앱 기록과 별도 Flue 저장소의 원문/실행 기록 범위를 함께 명시·검증합니다.
- 초기화는 대상·건수·영향을 먼저 보여 주고 사용자가 실행합니다. 이 요구는 기능 구현 승인이지 운영 데이터를 지금 삭제하라는 지시로 해석하지 않습니다.
- 엑셀 업로드 분석은 저장 전 미리보기·열/필드 확인·행별 오류·누락 안내를 제공하고 조용한 부분 저장을 막습니다. 가져오기와 현재 자료 내보내기, 택배 파일 생성은 서로 다른 흐름입니다. 실제 엑셀 파일 형태와 택배 양식은 아직 제공되지 않았습니다.

### 주문·자료 관리 구현 결정

- 불완전 후보도 `managed_orders`에 저장하며 필수 정보·현재 코드 견적에 문제가 없으면 `pending_payment`입니다. 이 단계는 재고 예약이 아닙니다. 방마다 활성 주문은 한 건이며 다른 주문 상담은 새 방에서 시작합니다.
- 확정은 별도 판매자 HTTP 명령입니다. 최신 자료/주문 버전, 실제 입금액·입금자명·주소 확인을 검사하고 SKU별 합산 수량 차감·주문 상태·확인자/시각·멱등 결과를 `BEGIN IMMEDIATE`로 함께 커밋합니다. 테스트는 실제 별도 프로세스 두 개를 경쟁시킵니다.
- 확정 주문의 상품명·옵션·단가·금액은 당시 값입니다. 삭제/초기화는 환불이나 재고 복원이 아닙니다. `order_origins`의 비개인정보 요청 ID/주문 ID는 삭제 후 재차감 방지 표식으로 남습니다.
- 엑셀 업로드는 2 MiB, 압축 해제 20 MiB, 500개 ZIP 항목, 시트당 10,000행·30열입니다. 실제 압축 해제도 크기를 제한합니다. 수식·링크·행 오류가 하나라도 있으면 가져오지 않습니다. 미리보기는 10분·최대 10개이며 적용 시 자료 버전을 다시 확인합니다.
- 상품 ID가 있으면 그 상품의 옵션 전체를 교체하며 파일에 없는 상품은 유지합니다. 상품/옵션 ID가 비어 있으면 이름·색상·사이즈로 매칭/생성하며 이름이 모호하면 거절합니다. 주문·대화 시트의 가져오기는 제공하지 않습니다.
- 채팅 초기화는 진행 중 실행을 거절하고 새 쓰기를 잠깐 차단한 뒤 전용 Flue 저장소와 앱 기록을 삭제합니다. 다른 SQLite·심볼릭 링크는 거절합니다. 외부 모델 서비스의 보관 기록과 내려받은 파일은 이 명령으로 지울 수 없습니다.
- 마피아 MCP 재검토에서 단일 쓰기 경로(`kf3a1087f73`), 실제 화면 실행(`k82f4ec7618`), 테스트 자료 정리(`ka6807a6552`)를 적용했습니다. 카드가 코드를 자동 심사한 것은 아닙니다. 현재 규모에서는 기존 SQLite 저장 계층을 유지하고 신규 ORM 전환은 이번 승인 흐름에 섞지 않았습니다.

### 문서 재점검의 근거

PRD, R-01~13, UC-01~06, 입출력 명세 3~7절, 상태/재고 규칙과 AC-01~23을 실제 API·Store 구현과 대조했습니다. 마피아 MCP의 수직 기능 완결(`k87a8cb40f0`), 문제 해결 여부 재검증(`kf7c518d278`), 사용자 요구를 조용히 빼지 않기(`k2edd1c94dc`) 원칙을 적용했습니다. 카드가 추가 기능을 정해 준 것으로 해석하지 않고, 사용자가 요청한 기능과 필요한 검증을 연결합니다.

## 유지하는 제품·기술 결정

- 실제 서비스로 이어갈 기반, 1인 셀러·에이전트 중심을 유지합니다. 상품/정책/주문/문서/일정은 허용된 도구로 읽고 근거 ID·버전을 반환합니다. 반복 업무 흐름을 줄이는 것이 목표이며 별도 매출 대시보드·쇼핑몰·결제를 추가하지 않습니다.
- Hono·TypeScript strict·Node.js 26.5.1 이상 27 미만·파일 SQLite를 사용합니다. 별도 DB 서버를 셀러에게 요구하지 않으며 `:memory:`는 테스트용입니다. 앱과 Flue DB는 분리하고 단일 Node 프로세스/Docker 영속 볼륨을 사용합니다.
- 주 실행기는 **Flue → OpenAI 직접 호출**, TypeSafe **Jev**는 선택적 문의 분류 도구입니다. 실제 자료 도구·코드 견적·제출 검증과 실행 이력을 사용하며 고정 샘플 답장으로 새 DM을 처리하지 않습니다.
- **Hermes·OpenAI Agents API·AI Gateway**는 사용자가 지정한 기술군이지만 현재 앱 실행 경로에는 미연결입니다. 주 실행기를 중복 연쇄하기보다 필요한 보조 역할·도구/세션/게이트웨이 호환성을 작게 검증해 연결합니다. 기존 Flue/SQLite 핵심 주문 흐름을 이 실험 때문에 미루지 않습니다.
- 모델·Provider 키는 env에서 서버만 읽습니다. 개발 Vite 프록시는 서버에서만 연결 토큰을 붙이고 빌드 웹은 HttpOnly 세션을 사용합니다. Codex의 Drive/Calendar/MCP 연결은 앱 인증으로 자동 상속되지 않습니다.
- 모델 기본 제한은 요청당 60초·모델 8회·도구 16회·모델당 출력 4,096토큰, 방 맥락 최근 40메시지/40,000자입니다. 통화 기준 비용 상한이나 품질 보장을 뜻하지 않습니다. 변경·실행 명령은 [백엔드 사용법](backend.md)을 기준으로 합니다.

## 승인·거래 경계

- 답장은 초안이며 판매자가 검토·복사해 직접 전송합니다. 인스타그램 직접 연동·자동 발송, 은행 자동 입금 확인, 택배 API 송장 발급은 첫 버전 제외 범위입니다.
- 고객의 입금 주장, 붙여넣은 판매자 대사, 이전 assistant 초안은 승인 근거가 아닙니다. 주문 후보 저장·분석·조회·내보내기로 재고를 차감하지 않습니다.
- 판매자 확정 명령은 승인 문맥·확인 금액/입금자명/수령지·주문 버전·상품/정책 버전·가용 재고·마감을 다시 검사하고 전 품목을 원자적으로 반영합니다. 실패 시 모두 롤백하며 다른 명령 키로 같은 주문을 요청해도 다시 차감하지 않습니다.
- 발송 등록·정정은 주문 상태/버전/시각/명령 키와 정정 사유를 검사해 송장·감사 이력을 함께 저장합니다. 재고와 주문 금액을 다시 변경하지 않습니다. 내보내기는 발송 완료를 뜻하지 않습니다.
- 확정 후 취소·환불·보상·주소 변경·재고 복구는 판매자 예외 처리이며 자동화 범위를 임의 확장하지 않습니다. 보관/삭제·운영 권한 등 미확정 사항은 [운영 기준](operations.md)을 따릅니다.

## 자료와 엑셀의 역할

- 현재 상품/정책/주문 근거의 원본은 판매자 범위 SQLite입니다. 가상 JSON은 초기/평가 자료이며 운영 정책이 아닙니다. 예시 문서는 최신 정책을 덮어쓰지 않습니다.
- 자료 가져오기: 판매자가 가진 엑셀을 분석하고 필드/행/오류와 저장 대상을 확인한 뒤 가져옵니다. 수식·외부 링크·과대 파일·식별자 충돌과 조용한 부분 저장을 막습니다. 필요한 열 대응은 쉬운 한글 안내와 미리보기로 제공하고 임의 추측을 확정하지 않습니다.
- 현재 데이터 내보내기: 상품·정책·주문·대화를 현재 저장된 값과 ID/버전으로 반출합니다. 과거 주문에 현재 가격·정책을 재적용하지 않습니다. 전화·우편번호는 문자열, 고객 입력은 수식으로 실행되지 않는 값으로 보존합니다.
- 택배용 내보내기: 확정 미발송 주문의 필수값·제외 사유·재내보내기 이력·실제 양식 버전을 확인합니다. 실제 택배사 업로드 양식이 제공되지 않았으므로 내부 공통 양식을 특정 택배사와 호환된다고 주장하지 않습니다.
- 상품/정책·주문·채팅 초기화는 독립 명령입니다. 자료를 비워도 샘플을 재생성하지 않고, 실행/조회/캐시/Flue 기록 및 백업과의 관계를 검증합니다. 주문 초기화를 취소·환불 또는 자동 재고 복구로 취급하지 않습니다.

## 검증과 완료 판정

1. 각 단계의 정상 흐름을 DB·API·화면까지 연결한 뒤 직접 실행하고, 같은 작업에서 실패·경계·재전송·격리·롤백을 검증합니다. 사용자에게 코드 실행 확인을 떠넘기지 않습니다.
2. 현재 Node 43개·Python 31개와 타입/린트/포맷/서버·웹 빌드, Docker, 가상 실제 모델·브라우저 검사는 [검증 계획](test-plan.md)의 범위만 통과한 것입니다. 주문 상태 전이/자료 관리 자동 검증을 실제 50건 모델 품질이나 전체 인수조건 통과로 확대하지 않습니다.

## 외부 자료가 필요한 지점

실제 엑셀 파일의 열 구성과 대상 택배사 업로드 양식·버전, 실제 판매 정책·사용 권한·말투 예시는 아직 지정되지 않았습니다. 구조와 가상 검증은 진행할 수 있으나 실제 파일/양식의 호환성·생성 답장 적합성은 자료 확보 후 별도로 검증합니다. 주소 API·Sheets·외부 캘린더는 필요한 인증/자료 ID와 최소 조회 권한을 확인한 뒤 연결합니다.
