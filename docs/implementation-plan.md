# 구현 순서와 결정 목록

상태: 단건 에이전트·웹/채팅, 주문/재고, 발송/정정·공통 엑셀과 자료 관리를 구현했습니다. 가상 DM 평가 실행기, 동명이인 검토와 일괄 DM 처리를 추가했습니다. 아래 제품 흐름과 미구현 범위를 기준으로 다음 작업을 진행합니다. 현재 명령·제한은 [백엔드 사용법](backend.md), 전체 완료 판정은 [인수조건](acceptance-criteria.md)을 따릅니다.

## 현재 구현과 제품 완성의 차이

제품의 완료 흐름은 **DM 입력·분류 → 근거 기반 초안/주문 추출 → 주문 후보 저장·수정 → 판매자의 입금·수령지 확인 → 주문 확정·재고 반영 → 주문 조회 → 수동 발송/송장 등록·정정 → 확정 미발송 주문의 택배 양식 내보내기**입니다. 읽기 에이전트나 자료 편집 화면만으로 제품이 완성됐다고 보지 않습니다.

현재 구현은 단건 DM/방 맥락·Flue/TypeSafe 도구·코드 견적·구조화 분석·복사용 초안·SQLite 보존, 주문 후보 저장/수정과 판매자 입금 확인·확정/원자적 재고 차감, 수동 발송/정정과 공통 엑셀까지 연결됩니다. 상품/옵션/정책 CRUD, 엑셀 미리보기/검증 후 가져오기, XLSX·JSON 현재 데이터 반출과 독립 초기화도 제공합니다. 분석 JSON의 `order_draft`는 자동으로 주문이 되지 않습니다.

수동 발송/송장 정정·변경 전후 이력과 공통 택배 엑셀/열 설정을 구현했습니다. 사용자가 택배사 미정을 선택했으므로 실제 접수 양식 호환성을 주장하지 않습니다.

**아직 미구현**: 실제 택배 양식 어댑터, 주문/대화 재가져오기. 상품·정책 가져오기는 전용 양식과 한글 열 별칭을 지원하며 임의의 엑셀 구조를 모델이 추측해 자동 변환하지 않습니다. 자동 테스트·소량 실검증은 전체 실제 DM 품질 통과가 아닙니다.

### 초기 기획과 남은 차이

2026-11-06 [원문 고정 리비전](https://gist.githubusercontent.com/peppone-choi/13f04536847d32b1a62ac035b2d1856d/raw/eca4f2e8655353920c68d7fc04aed30701f78d52/InByeolChongmu01.md)의 섹션 3~5를 다시 읽고 실제 API·도구·화면·검증 명령과 대조했습니다. 원문은 변경하지 않으며 아래는 현재 상태와 다음 작업입니다.

- **핵심 흐름 구현**: 단건 분류/추출/누락 안내/근거 기반 초안, 판매자 주문 저장·입금 확인/확정·재고, 주문 검색, 발송/정정 이력, 공통 엑셀을 DB·API·웹에 연결했습니다. 자료 CRUD·엑셀 가져오기/현재 데이터 반출·독립 초기화는 이후 추가 요구까지 구현했습니다. 기능 연결과 모델 품질 통과는 다릅니다.
- **일괄 접수와 검토 순서 구현**: SQLite에 건별 고객·맥락·원문과 진행 상태를 보존하고 실패한 건만 다시 분석합니다(R-01·10/AC-15). 클레임과 확인 필요 건을 먼저 표시합니다.
- **추출값 원문 대조 구현**: 저장된 고객 발화에 있는 수령인·연락처·주소·우편번호·입금자명에 강조 구간과 이동 버튼을 제공합니다.
- **원문의 미완성 기능**: 송장 조회 링크 생성과 실제 택배사 양식(R-09/AC-14)이 남았습니다.
- **부분 지원**: 말투 정책은 수정할 수 있지만 실제 판매자 DM 20~30개를 관리·조회하는 흐름과 적합성 검증은 없습니다. 답장 편집도 화면 메모리이며 판매자의 수정본을 저장·재사용하지 않습니다. 자동 말투 학습은 기존 첫 버전 제외 결정대로 후속입니다. 정책 사실과 말투 예시의 권한은 분리해야 합니다.
- **품질 검증**은 [검증 계획](test-plan.md#가상-dm-평가-실행기)에서 실행 결과와 수동 판정을 구분합니다. 실제 비식별 DM 50건과 실제 셀러 1주 효과는 미측정입니다.

`DM-009`에서는 방에 연결된 고객과 주문 당시 계정이 다르면 기존 조회가 0건을 반환했습니다. 현재는 고객 원문의 이름이 같은 판매자의 주문에 일치할 때 후보 ID를 반환합니다. 검토 화면에서 판매자가 주문 상세를 선택하며 에이전트의 상세 조회는 고객 범위를 유지합니다. 후보가 답장 근거로 쓰이거나 답장·주문 초안이 함께 제출되면 거절합니다.

### 다음 구현 순서

1. **에이전트 평가 실행기와 조회 계약 보완 (구현)**. `npm run --silent eval:agent -- --live`로 격리된 가상 40건을 실행합니다. 코드로 판정할 기대값과 사람이 읽을 초안을 구분하고, 실패 사례의 분류·누락·근거를 재현해 수정합니다. 모델 호출 수와 시간은 다음 일괄 처리의 실행 한도를 정할 때 사용합니다.
2. **여러 DM 일괄 처리와 우선 검토 (구현)**: 기존 채팅 수신 서비스 위에 SQLite 배치/항목 상태와 접수·진행 조회·실패 건 재시도 API, 웹의 건별 아이디/맥락/원문 입력 미리보기를 연결합니다. 고객 경계를 임의 추측해 긴 텍스트를 자동 합치지 않습니다. 가상 40건의 이번 전체 실행은 단건 최대 21.145초·모델 5회였습니다. 첫 버전은 순차 실행과 최대 10건을 선택했습니다. 기본 단건 60초·모델 8회·도구 16회 한도 기준으로 최초 분석 한 묶음은 최대 모델 80회·도구 160회이며, 서버의 단건 분석 시간 예산 합은 10분입니다. 대기 건은 화면을 다시 연 뒤 명시적으로 이어서 실행합니다. 항목별 요청 ID/상태/실패를 유지하며 재시작 후 상태 복원과 재호출을 구분합니다. 결과 미확인 요청은 같은 ID 조회/재시도, 종료된 실패 재분석은 명시적인 새 ID입니다. 클레임을 먼저, 다음 확인 필요를 보여 주고 같은 우선순위의 순서를 안정적으로 유지합니다. AC-15의 DM-001·002·009·020 혼합/부분 실패/재시도에서 다른 건의 추가 모델 호출·주문 확정·재고 변경이 없음을 확인합니다.
3. **판매자 답장 보완**: 판매자가 선택한 말투 예시를 자료 도구로 읽고 편집본 저장/명시적 재사용을 연결하되 예시를 가격·정책·입금 승인 근거로 쓰지 않습니다. 기존 복사용 블록 형식과 정책 우선순위를 유지합니다. 택배사별 허용된 공식 조회 URL이 정해지면 저장된 송장으로 링크만 생성하며 실제 배송 상태를 확인했다고 표현하지 않습니다.
4. **실제 택배 양식과 운영 전 준비**: 대상 택배사/접수 프로그램·양식 버전을 확보한 뒤 어댑터와 필수 열/발송인/수령인/자료형을 검증합니다. 대상 미정 동안 공통 명단을 유지하고 AC-14는 미검증으로 남깁니다. 실제 개인정보를 넣기 전 단일 판매자 운영 인증·접근 제한·보관/삭제·외부 전송 범위·백업 복구·확정 후 취소/환불/주소 정정 절차를 준비합니다. 삭제를 취소·재고 복구로 대신하지 않습니다. 권한 있는 비식별 50건과 판매자 판정으로 품질 목표를 평가하고, 도입 전 기준선을 측정한 뒤 1주 사용 효과를 확인합니다.

DM-028은 후보 ID와 별도 입금 주장·입금자명 추출을 같은 기준으로 재검증했습니다. 입금자명을 주문 고객의 이름으로 해석하지 않으며 다른 계정의 주문은 판매자 확인 전까지 연결하지 않습니다. 일괄 처리에서는 고객·방 격리, 실패 건만 재호출, 주문·재고 보존을 회귀로 검사합니다.

### 원문과 이후 기술 요청의 구분

원문의 Sheets는 저장 수단 후보였으며 이후 사용자 결정에 따라 파일 SQLite·엑셀을 기반으로 유지합니다. 외부 Sheets·문서·캘린더 계정 연결, 주소 검색 API, 주문/대화 재가져오기는 별도 남은 확장입니다. 현재 일정 도구는 로컬 상품 마감/정책 값을 읽으며 외부 캘린더 OAuth가 아닙니다. 실제 주소 검색이 없어 현재 분석은 `not_checked`만 허용합니다. 기본 주소 대조와 실제 주소 API 성공을 혼동하지 않습니다.

사용자가 지정한 Hermes·OpenAI Agents API·AI Gateway도 미연결 과제로 유지합니다. 에이전트 평가 기준을 만든 뒤 AI Gateway 추론 경로부터 호환성/인증/도구 실행/재시도/관측을 작은 범위로 검증하고, Hermes·OpenAI Agents API는 Flue와 역할/세션 경계를 정해 각각 연결합니다. 제품 흐름에 쓰이지 않는 SDK 추가만으로 연결 완료라고 하지 않습니다. 이 검증 전 기존 실행기를 대체하거나 중복 연쇄하지 않습니다.

인스타 자동 전송·은행 자동 입금 확인·택배 API 송장 발급·사진 인식·다계정/다인원·쇼핑몰·매출 대시보드·과금은 첫 버전 제외/후속 결정을 유지합니다. 이 항목의 부재를 최초 MVP의 미구현 필수 기능으로 집계하지 않습니다.

### 사용자가 확정한 추가 요구

- 상품·정책은 기존 값 수정뿐 아니라 추가·삭제도 지원합니다. 과거 주문의 저장 당시 금액·발송 사실은 별도로 보존합니다.
- 상품·정책 초기화는 **샘플 없이 모두 비우며 주문과 대화는 유지**합니다. 재시작으로 샘플을 다시 채우지 않습니다.
- 주문 초기화와 채팅 기록 초기화는 각각 별도 동작이며 다른 데이터 영역을 함께 지우지 않습니다. 채팅 초기화는 앱 기록과 별도 Flue 저장소의 원문/실행 기록 범위를 함께 명시·검증합니다.
- 초기화는 대상·건수·영향을 먼저 보여 주고 사용자가 실행합니다. 이 요구는 기능 구현 승인이지 운영 데이터를 지금 삭제하라는 지시로 해석하지 않습니다.
- 엑셀 업로드 분석은 저장 전 미리보기·열/필드 확인·행별 오류·누락 안내를 제공하고 조용한 부분 저장을 막습니다. 가져오기와 현재 자료 내보내기, 택배 파일 생성은 서로 다른 흐름입니다. 실제 엑셀 파일 형태와 택배 양식은 아직 제공되지 않았습니다.

### 발송·택배 파일 결정

- 최초 발송은 확정 주문, 정정은 발송 상태만 허용합니다. 주문·송장·정정 이력·명령 결과를 같은 트랜잭션으로 저장하고 재고·금액은 변경하지 않습니다. 과거 JSON 주문과 새 관리 주문은 중복 저장하지 않으며 에이전트 조회도 같은 최신 값을 읽습니다.
- 택배사 미정이라는 사용자 답에 따라 공통 명단의 열 이름/순서/필수값을 설정하는 방식으로 구현했습니다. 미확정/취소/기발송/필수값 누락은 사유와 함께 제외합니다. 열 설정의 기본값은 우편번호 선택입니다. 확정 후 수령 정보 변경은 이 작업에 섞지 않았습니다.
- 내보내기는 미리보기 fingerprint로 상태 변경을 검출합니다. 같은 명령 키는 같은 파일 ID, 새 파일 생성에는 과거 내보낸 주문의 중복 접수 확인이 필요합니다. 파일용 행 스냅샷을 저장해 이후 주문/양식 수정으로 기존 파일 내용이 바뀌지 않게 합니다.
- 주문 삭제 후 파일에 원래 개인정보가 남아 재다운로드되는 것을 막기 위해 해당 주문 포함 파일의 스냅샷을 폐기합니다. 배치 메타데이터는 남겨 다른 주문의 이전 내보내기 경고를 유지합니다. 전체 주문 초기화는 파일/이력도 지우지만 열 설정은 유지합니다.

### 주문·자료 관리 구현 결정

- 불완전 후보도 `managed_orders`에 저장하며 필수 정보·현재 코드 견적에 문제가 없으면 `pending_payment`입니다. 이 단계는 재고 예약이 아닙니다. 방마다 활성 주문은 한 건이며 다른 주문 상담은 새 방에서 시작합니다.
- 확정은 별도 판매자 HTTP 명령입니다. 최신 자료/주문 버전, 실제 입금액·입금자명·주소 확인을 검사하고 SKU별 합산 수량 차감·주문 상태·확인자/시각·멱등 결과를 `BEGIN IMMEDIATE`로 함께 커밋합니다. 테스트는 실제 별도 프로세스 두 개를 경쟁시킵니다.
- 확정 주문의 상품명·옵션·단가·금액은 당시 값입니다. 삭제/초기화는 환불이나 재고 복원이 아닙니다. `order_origins`의 비개인정보 요청 ID/주문 ID는 삭제 후 재차감 방지 표식으로 남습니다.
- 엑셀 업로드는 2 MiB, 압축 해제 20 MiB, 500개 ZIP 항목, 시트당 10,000행·30열입니다. 실제 압축 해제도 크기를 제한합니다. 수식·링크·행 오류가 하나라도 있으면 가져오지 않습니다. 미리보기는 10분·최대 10개이며 적용 시 자료 버전을 다시 확인합니다.
- 상품 ID가 있으면 그 상품의 옵션 전체를 교체하며 파일에 없는 상품은 유지합니다. 상품/옵션 ID가 비어 있으면 이름·색상·사이즈로 매칭/생성하며 이름이 모호하면 거절합니다. 주문·대화 시트의 가져오기는 제공하지 않습니다.
- 채팅 초기화는 진행 중 실행을 거절하고 새 쓰기를 잠깐 차단한 뒤 전용 Flue 저장소와 앱 기록을 삭제합니다. 다른 SQLite·심볼릭 링크는 거절합니다. 외부 모델 서비스의 보관 기록과 내려받은 파일은 이 명령으로 지울 수 없습니다.
- 마피아 MCP 재검토에서 단일 쓰기 경로(`kf3a1087f73`), 실제 화면 실행(`k82f4ec7618`), 테스트 자료 정리(`ka6807a6552`)를 적용했습니다. 카드가 코드를 자동 심사한 것은 아닙니다. 현재 규모에서는 기존 SQLite 저장 계층을 유지하고 신규 ORM 전환은 이번 승인 흐름에 섞지 않았습니다.

### 문서 재점검의 근거

PRD, R-01~13, UC-01~06, 입출력 명세 3~7절, 상태/재고 규칙과 AC-01~23을 실제 API·Store 구현과 대조했습니다. 마피아 MCP의 수직 기능 완결(`k87a8cb40f0`), 문제 해결 여부 재검증(`kf7c518d278`), 사용자 요구를 조용히 빼지 않기(`k2edd1c94dc`) 원칙을 적용했습니다. 카드가 추가 기능을 정해 준 것으로 해석하지 않고, 사용자가 요청한 기능과 필요한 검증을 연결합니다.

## 유지하는 제품·기술 결정

- 실제 서비스로 이어갈 기반, 1인 셀러·에이전트 중심을 유지합니다. 상품/정책/주문/문서/일정은 허용된 도구로 읽고 근거 ID·버전을 반환합니다. 반복 업무 흐름을 줄이는 것이 목표이며 별도 매출 대시보드·쇼핑몰·결제를 추가하지 않습니다.
- Hono·TypeScript strict·Node.js 26.5.1 이상 27 미만·파일 SQLite를 사용합니다. 별도 DB 서버를 셀러에게 요구하지 않으며 `:memory:`는 테스트용입니다. 앱과 Flue DB는 분리하고 단일 Node 프로세스/Docker 영속 볼륨을 사용합니다.
- 주 실행기는 **Flue → 설정에서 선택한 OpenAI 또는 Claude API 직접 호출**이며 TypeSafe **Jev**는 선택적 문의 분류 도구입니다. 실제 자료 도구·코드 견적·제출 검증과 실행 이력을 사용하며 고정 샘플 답장으로 새 DM을 처리하지 않습니다.
- 판매자 등록 채팅은 같은 공급자 설정으로 한 건씩 입력을 추출합니다. 모델 결과는 검증된 편집 폼에만 전달하며 저장은 기존 Store 명령과 자료 버전 검사를 거칩니다.
- **Hermes·OpenAI Agents API·AI Gateway**는 사용자가 지정한 기술군이지만 현재 앱 실행 경로에는 미연결입니다. 주 실행기를 중복 연쇄하기보다 필요한 보조 역할·도구/세션/게이트웨이 호환성을 작게 검증해 연결합니다. 기존 Flue/SQLite 핵심 주문 흐름을 이 실험 때문에 미루지 않습니다.
- 모델·Provider 키는 env에서 서버만 읽습니다. 개발 Vite 프록시는 서버에서만 연결 토큰을 붙이고 빌드 웹은 HttpOnly 세션을 사용합니다. Codex의 Drive/Calendar/MCP 연결은 앱 인증으로 자동 상속되지 않습니다.
- 모델 기본 제한은 요청당 60초·모델 8회·도구 16회·모델당 출력 4,096토큰, 방 맥락 최근 40메시지/40,000자입니다. 통화 기준 비용 상한이나 품질 보장을 뜻하지 않습니다. 변경·실행 명령은 [백엔드 사용법](backend.md)을 기준으로 합니다.

## 승인·거래 경계

- 답장은 초안이며 판매자가 검토·복사해 직접 전송합니다. 인스타그램 직접 연동·자동 발송, 은행 자동 입금 확인, 택배 API 송장 발급은 첫 버전 제외 범위입니다.
- 고객의 입금 주장, 붙여넣은 판매자 대사, 이전 assistant 초안은 승인 근거가 아닙니다. 주문 후보 저장·분석·조회·내보내기로 재고를 차감하지 않습니다.
- 판매자 확정 명령은 승인 문맥·확인 금액/입금자명/수령지·주문 버전·상품/정책 버전·가용 재고·마감을 다시 검사하고 전 품목을 원자적으로 반영합니다. 실패 시 모두 롤백하며 다른 명령 키로 같은 주문을 요청해도 다시 차감하지 않습니다.
- 발송 등록·정정은 주문 상태/버전/시각/명령 키와 정정 사유를 검사해 송장·감사 이력을 함께 저장합니다. 재고와 주문 금액을 다시 변경하지 않습니다. 내보내기는 발송 완료를 뜻하지 않습니다.
- 확정 후 취소·환불·보상·주소 변경·재고 복구는 판매자 예외 처리이며 자동화 범위를 임의 확장하지 않습니다. 보관/삭제·운영 권한 등 미확정 사항은 [운영 기준](operations.md)을 따릅니다.

## 자료와 엑셀의 역할

- 현재 상품/정책/주문 근거의 원본은 판매자 범위 SQLite입니다. 가상 JSON은 초기/평가 자료이며 운영 정책이 아닙니다. 예시 문서는 최신 정책을 덮어쓰지 않습니다.
- 자료 가져오기: 판매자가 가진 엑셀을 분석하고 필드/행/오류와 저장 대상을 확인한 뒤 가져옵니다. 수식·외부 링크·과대 파일·식별자 충돌과 조용한 부분 저장을 막습니다. 필요한 열 대응은 쉬운 한글 안내와 미리보기로 제공하고 임의 추측을 확정하지 않습니다.
- 현재 데이터 내보내기: 상품·정책·주문·대화를 현재 저장된 값과 ID/버전으로 반출합니다. 과거 주문에 현재 가격·정책을 재적용하지 않습니다. 전화·우편번호는 문자열, 고객 입력은 수식으로 실행되지 않는 값으로 보존합니다.
- 택배용 내보내기: 확정 미발송 주문의 필수값·제외 사유·재내보내기 이력·실제 양식 버전을 확인합니다. 실제 택배사 업로드 양식이 제공되지 않았으므로 내부 공통 양식을 특정 택배사와 호환된다고 주장하지 않습니다.
- 상품/정책·주문·채팅 초기화는 독립 명령입니다. 자료를 비워도 샘플을 재생성하지 않고, 실행/조회/캐시/Flue 기록 및 백업과의 관계를 검증합니다. 주문 초기화를 취소·환불 또는 자동 재고 복구로 취급하지 않습니다.

## 검증과 완료 판정

1. 각 단계의 정상 흐름을 DB·API·화면까지 연결한 뒤 직접 실행하고, 같은 작업에서 실패·경계·재전송·격리·롤백을 검증합니다. 사용자에게 코드 실행 확인을 떠넘기지 않습니다.
2. 현재 Node 62개·Python 31개와 타입/린트/포맷/서버·웹 빌드, Docker, 가상 실제 모델·브라우저 검사는 [검증 계획](test-plan.md)의 범위만 통과한 것입니다. 주문 상태 전이/자료 관리 자동 검증을 실제 50건 모델 품질이나 전체 인수조건 통과로 확대하지 않습니다.
3. 가상 40건 평가의 자동 대조와 수동 판정은 [검증 계획](test-plan.md#가상-dm-평가-실행기)에 기록합니다. 실제 50건 평가는 남아 있습니다. 실제 50건 목표는 분류 90% 이상·사용 가능한 초안 70% 이상·근거 없는 정보 0건·추출 95% 이상·필수 누락 감지 100%입니다.
4. 실제 자료 사용 권한·판매 정책·외부 전송/보관·운영 인증·백업/복구를 확인한 뒤 실제 셀러 1주 사용 효과를 평가합니다. 단건의 금액 일치나 모델 없는 자동 테스트를 품질 수치로 보고하지 않습니다.
5. 완료 보고 전에 README·관련 계약·AGENTS.md와 실제 코드/명령/검증 결과를 대조합니다. 미구현 기능은 지원 기능 목록에 올리지 않습니다.

## 외부 자료가 필요한 지점

실제 엑셀 파일의 열 구성과 대상 택배사 업로드 양식·버전, 실제 판매 정책·사용 권한·말투 예시는 아직 지정되지 않았습니다. 구조와 가상 검증은 진행할 수 있으나 실제 파일/양식의 호환성·생성 답장 적합성은 자료 확보 후 별도로 검증합니다. 주소 API·Sheets·외부 캘린더는 필요한 인증/자료 ID와 최소 조회 권한을 확인한 뒤 연결합니다.
