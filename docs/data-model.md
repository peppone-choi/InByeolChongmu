# 데이터 모델과 상태 규칙

상태: 논리 모델 초안. DB 엔진·실제 테이블·마이그레이션은 없습니다.

## 데이터와 관계

- 판매자: 상품·정책·주문·DM·승인·내보내기의 소유자입니다. 모든 조회는 판매자 범위로 제한합니다.
- 상품 → 옵션: `product_id` 아래 여러 `sku`가 있습니다. 가격·가용 재고는 옵션 단위입니다. 별칭은 여러 상품과 겹칠 수 있어 고유 키로 사용하지 않습니다.
- 주문 → 주문 품목: 주문 ID는 고유하며 품목은 SKU·수량·확정 가격 스냅샷을 보존합니다. 과거 주문 금액을 현재 상품 가격으로 다시 계산하지 않습니다.
- 저장 금액: 확정 당시 상품합·할인·배송비·총액을 보존합니다. 자료 검사는 이 값의 정수 범위와 산술을 확인하며 현재 할인·배송비를 재적용하지 않습니다. 정책 적합성 대조가 필요하면 당시 정책 버전을 별도로 보존해야 합니다.
- 분석 결과: 요청 ID·원문 참조·자료 버전·근거·검증 결과를 갖습니다. 주문 후보와 실제 저장된 주문은 별개입니다.
- 승인 명령: 판매자 범위의 `command_id`, 요청 내용 식별값, 결과, 승인자·시각을 저장합니다. 같은 키의 다른 내용을 거절합니다.
- 내보내기: 주문 ID 목록·양식 버전·시각·결과를 기록합니다. 파일과 주문 상태는 독립입니다.

## 주문 상태 전이

`draft → pending_payment → confirmed → shipped`

- `draft`: 필수값 미완성 또는 수정 중인 저장 후보입니다.
- `pending_payment`: 필수값·정책 검증을 통과했고 입금 확인을 기다립니다. 재고 예약은 하지 않습니다.
- `confirmed`: 판매자 입금·수령지 확인과 최신 재검사 후 주문 확정·재고 차감을 원자적으로 완료했습니다.
- `shipped`: 판매자가 실제 발송·송장 정보를 등록한 상태입니다. 파일 내보내기만으로 바뀌지 않습니다.
- `cancelled`: 확정 전 후보를 판매자가 취소한 상태입니다. `draft/pending_payment → cancelled`만 초기 구현 대상으로 제안합니다.

확정 전 내용을 수정하면 `version`을 올리고 다시 검증합니다. 필수값이 빠지면 `draft`로 돌립니다. 확정·발송 이후 취소·환불·주소 변경·재고 복구는 판매자 예외 처리이며 자동 상태 전이를 구현하지 않습니다. 실제 처리 방법과 감사 기록은 운영 도입 전에 정해야 합니다.

`confirmed → shipped`는 판매자의 `register_shipment` 명령으로만 진행합니다. 송장·택배사·발송일·감사 기록을 함께 저장하고 버전을 올립니다. 정정은 `update_shipment`로 `shipped → shipped`를 유지하며 변경 전후와 사유를 기록합니다. 두 명령의 권한·멱등성·허용 시각·실패 응답은 [입출력 명세 7절](io-spec.md)의 계약을 따릅니다. 재등록·정정·재시도는 재고와 금액을 바꾸지 않습니다.

## 재고·금액 불변 조건

1. 분석·초안 저장·조회·내보내기는 재고를 바꾸지 않습니다.
2. 확정 시 모든 품목을 검증하고 함께 차감합니다. 재고는 음수가 될 수 없습니다.
3. 같은 주문은 확정 명령 키가 달라도 한 번만 차감합니다. 동시 확정에는 버전 검사와 원자적 갱신이 필요합니다.
4. 확정 전 가격·정책·재고·마감이 바뀌면 재검토를 요구합니다. 새 금액을 조용히 확정하지 않습니다.
5. 샘플 상품 재고는 기존 주문 반영 후 스냅샷입니다. 샘플 주문 적재 시 다시 차감하지 않습니다.

## 개인정보와 이력

연락처·주소 원문은 필요한 저장소에만 보관하고 일반 로그에서 제외합니다. 정규화 값으로 원문을 덮어쓰지 않습니다. 보관·삭제 기간, 백업 삭제 반영, 확정 후 변경 이력은 [운영 기준](operations.md)의 미정 사항입니다.
